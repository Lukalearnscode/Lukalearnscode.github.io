Localization Pipeline

An AI localization pipeline for EN↔ZH game and creative text. I designed it, I run real client work through it, and I keep rebuilding the parts that fail. It is not open source — it is a personal production system, tuned to how I work — so this page does the opposite of a repository: it explains the design, part by part, and why each part exists.

The one-sentence version: a language model translating in one pass produces fluent text with silent errors, and everything in this pipeline exists to catch a specific way that fluent text goes wrong.

The problem

Machine translation's classic failure is not clumsiness any more. Modern models write smoothly. The failure is drift under the smoothness: a clause quietly dropped, a nuance quietly added, a character name translated one way in chapter one and another way in chapter nine. Each segment reads fine on its own. The errors only exist across segments, or between the translation and a source the reader never sees.

Worse, a model asked whether its own work is good will say yes. Self-review by the same model is close to worthless — it re-approves its own habits. So the real engineering problem is not translation. It is verification: how do you get honest evidence of quality out of a system whose components all sound confident?

The pipeline's answer has three parts: split the work into phases that each leave checkable evidence, split review across models that cannot see each other's reasoning, and put mechanical gates between the model and the word "done".

Design idea 1: prompts are generated, not written

A game UI string, a legal clause, and a line of flirtatious banter need different translation rules — and the rules for translating into Chinese are not the mirror image of the rules for translating out of it. A single thousand-line master prompt where every project uses thirty relevant lines is noise for the model and unmaintainable for me.

So the system is a meta prompt. It stores rules for generating prompts. Each project starts with an analysis phase — text type, audience, direction, register, terminology, risk — and the translation and review prompts are then assembled for that project specifically, with irrelevant rule branches deleted by a compiler script rather than left in to dilute attention. The skill's job is to make a bespoke rule set cheap.

The pipeline: nine phases

One line: read the file, understand the project, generate the prompts, translate, review in three stages, restore markup, run global QA, deliver, and feed what went wrong back into the system. Every phase has a "definition of done" — files that must exist and checks that must pass — verified by a script, not by the model's word.

0
Intake
Unpack the file into an immutable machine-readable source of truth: segment IDs, order, inline tags, speaker fields. Health checks run here — sentences the CAT tool split across segments, metadata left over from earlier edits.
1
Analysis & routing
What kind of job is this — translation, review, client trial? What domain, direction, risk level? Which models draft and which review? Decisions land in a route card; repeated and near-identical sentences are scanned before anything is translated.
2
Prompt generation
Assemble three prompts from the analysis: one for drafting, one for blind review, one for the bilingual final review. A compiler strips every rule branch that does not apply to this project.
3
Translation
Batched by meaning, never splitting a dialogue or scene, with a rolling recap carried between batches. Each batch is drafted in three explicit steps — understand, translate, polish — and the raw output is kept as evidence. Coverage is reconciled by script: every segment ID in, every segment ID out.
4
Three-stage review
The heart of the system — mechanical preflight, blind review, bilingual final adjudication. Detailed below.
5
Tag restoration
Inline markup goes back into the translated text and is verified — count, content, nesting, and whether each tag wraps the right words. This layer became its own open-source tool: memoQ Tag Transfer.
6
Global QA
Whole-document scans that per-segment review is structurally blind to: punctuation locale, quote-style consistency across the full text, terminology drift, numbers and dates, source-language leftovers — plus a quality score bound to the hash of the exact final text.
7
Delivery
One gate, one command. It re-runs every check itself rather than reading old reports, and nothing ships until it exits clean. Output is whatever the client workflow needs — TMX for CAT-tool import, a bilingual review table, or same-format text.
8
Learning
Every error found late gets triaged: project-specific fixes go into that project's assets; general lessons enter a quarantine queue and only merge into the permanent rules after human confirmation. The pipeline is supposed to be better after every job.

The heart: three review stages

Review is where most translation quality systems are weakest, because they use one reviewer who sees everything and trusts their own judgement. This pipeline deliberately controls what each reviewing party is allowed to see.

Stage 1

Mechanical preflight

Scripts, not models. Tag counts, placeholders, glossary compliance, punctuation locale, batch-internal consistency, known-defect regression.

Sees: everything countable.

Stage 2

Blind review

A different model family reads the translation without the source — the reader's seat. It reports findings; it changes nothing.

Sees: target text only.

Stage 3

Bilingual final

A full source-against-target pass that adjudicates every blind finding and checks the whole text, then signs off — or blocks.

Sees: both sides, plus all evidence.

Stage 1 — mechanical preflight. A standing rule in this system: anything that amounts to counting is decided by a script, never by a language model. Models miscount, and worse, they miscount confidently. So tags, placeholders, numbers, glossary hits, punctuation, and previously-seen defect patterns are all scanned by code with exit codes, and the results enter the later prompts as established fact. Human and model attention is saved for what scripts cannot express.

Stage 2 — blind review. The blind reviewer reads the translation the way the player will: with no source text to lean on. That isolation is physical, not honorary — a fresh context that has never seen the source. Two hard rules. First, the blind reviewer must be a different provider and a different model family from the drafting model, because a model re-reading its own output will pass its own habits; a changed persona or prompt does not count as a changed model, and a validation script enforces this. Second, the blind reviewer's opinions are findings, not edits. It can say a line reads stiff; it cannot touch the text.

Stage 3 — bilingual final. The final reviewer sees everything: source, target, the mechanical reports, and every blind finding. It adjudicates each finding one by one, re-reads the whole text against the source, and has two disciplines that took real failures to learn. One: fire at meaning, not at form — block additions, omissions and distortions of meaning, but do not drag natural phrasing back toward the source's word order in the name of fidelity. Two: judge the issue and the proposed fix separately — a bad suggested fix does not mean the underlying problem is not real. Without that split, valid issues get silently closed because their first proposed fix was wrong.

Design idea 2: the model's word is not evidence

A model that has just finished a task and is asked "did you do it properly?" will, in the same breath and the same context window, say yes. Its own sign-off inflates. So the release decision was moved outside the model entirely:

Every phase must leave artifacts — five machine-readable files per project recording the source truth, the target text, every review verdict, and every check result. An independent validator reconciles them: coverage must be exactly equal, every blind finding must have an adjudication, every claimed check must have real output. The final gate re-runs every scan itself on the exact bytes about to ship, and the scan results are bound to the hash of that version — a green light obtained on last week's draft is worthless for today's.

One asymmetric rule I'm fond of: absence is legal, false claims are not. If a check did not run and nothing says it ran, the gate flags it and work continues honestly. If the ledger claims a check ran and the evidence file is missing, that is an automatic red. The rule targets the actual failure mode of language models, which is not laziness — it is confident overstatement.

Design idea 3: the pipeline must learn

Phase 8 is the part I would keep if I had to delete everything else. After every job, errors that were caught late get sorted: fixes that only matter for this client go into the project's assets; anything general becomes a candidate lesson. Candidate lessons sit in a quarantine file and are only merged into the permanent rules after I confirm them — an overreaction to one weird project should not contaminate the system forever.

The sharpest lessons skip prose entirely and become code: a defect that slipped through once is added to a known-defect library as a regression scan plus a test, so the same bug can never ship twice. And the pipeline now takes exams — bilingual corpus samples with defects deliberately planted, scored on recall. Current result: 11 of 11 planted defects caught after a scoring correction, on a 42-segment paper. The exam rules include one that sounds paranoid and is not: any context that has read the answer key is burned as a test-taker, forever. Leakage does not announce itself.

Does it work?

Two blind benchmarks against professionally shipped translations, run with the reference sealed until after scoring:

A Chinese-developed visual novel on Steam, ZH→EN: the pipeline's translation scored at parity with the shipped official English (8.30 vs 8.25 on a seven-dimension weighted rubric — effectively a tie). A published tech biography, EN→ZH against the commercial Chinese edition: comparable quality, each side winning different dimensions.

The pattern across both is consistent and honest: this system wins the floor and loses the ceiling. It is better than shipped human baselines at completeness, terminology consistency, and zero grammatical hard errors — the blind runs caught real omissions and real grammar mistakes in the official versions. It is still behind the best human work at native liveliness, the spark in a child character's voice. That split is not an accident; it is the design. Review layers exist to make the floor unbreakable. The ceiling is a different project — curated exemplars and per-line candidate sprints — and it is explicitly unfinished.

What I got wrong along the way

Paper guardrails. The batching safeguard — split long documents so context stays coherent — was documented, implemented as a function, and never actually wired into the main path. The script sent whole files to the API in one call for weeks, with zero errors reported. Since then the rule is: a guardrail exists only when it is on the execution path and you have watched it fire. New checks are wired in by first making an existing test fail.

The em-dash incident. Translating a book chapter into Chinese, the drafting model quietly added Chinese em-dashes to 13 of 38 segments — the source had none. All three review stages passed it; each layer was looking at more "important" things. It was caught because a human reader felt one paragraph was slightly off. The fix was not "pay more attention": it became a mechanical rule — compare dash counts between source and target — which flagged 15 segments the day it was written and zero after the cleanup. A human's vague "this feels odd" is often the entrance to a systematic defect; the job is to convert the feeling into a scanner.

Tests that quietly stop testing. A test that verifies a function works proves nothing about whether the function is ever called. I shipped guards whose unit tests passed while the call site had been deleted, and assertions loose enough that a table header satisfied a check meant for a full sentence. Same day, three separate instances. The fix is structural: test through the real entry point, and make assertions precise enough that they can actually fail.

Stack

Python and lxml, no framework. Runs from the command line as an instruction system on top of large language models — process documents, prompt templates, thirty-odd checking scripts with exit codes, and about eight thousand lines of tests, most of which exist because something real once got through. Drafting and review are split across different model families per project (DeepSeek, Claude, and others), which is a load-bearing design decision, not a convenience.

The tag-restoration layer is open source as memoQ Tag Transfer.

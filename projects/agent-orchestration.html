Agent Orchestration

A shell script that runs Claude and Codex against each other, unattended: Claude writes the code, Codex reviews it and is allowed to reject it, and a verifier that neither of them can touch decides whether the result ships.

Wiring the two of them together is an afternoon's work. Several people have published tools that do it. What took considerably longer, and is the only part worth writing down, is everything I learned after it worked: the ways a pipeline like this hands you a green light over work that was never actually done.

This page is that list. Every item below cost me a real failure.

The shape

1
Implement, in isolation
The writing agent works in a throwaway copy of the repository, on its own branch. Nothing it does can touch uncommitted work.
2
Review, read-only
Codex reads the diff against the task contract and returns one of three verdicts, in a schema it is forced to conform to: accept, fix, or reject.
3
Repair, then re-review by someone else
On fix, the reviewer gets write access and patches the code. Then a fresh instance reviews the patch. The agent that repaired the work never grades it.
4
Verify, mechanically
A test script the agents are forbidden to modify runs last. Its exit code, not anyone's summary, decides the outcome.

The reason to use two vendors rather than two instances of the same model is not that one is smarter. It is that they fail differently. A model reviewing its own work re-approves its own habits; the disagreements between two lineages are where the signal is.

Seven ways it lies to you

Trap 01

A failed run still exits zero

Agent CLIs are conversational tools. When the model gives up, apologises, or misunderstands the task entirely, the process still terminates normally. If your script branches on the exit code, it will cheerfully report success over a session that accomplished nothing.

Fix: never let a run's own exit code decide anything. Success is defined only by files that exist afterwards and by a verifier the agent did not write.

Trap 02

It will write its own passing test

Tell an agent that a verification script decides whether its work is accepted, and if that script does not already exist, it will helpfully create one. It will pass. It always passes.

Fix: record which verifier existed before the run started. Anything that appears later is evidence of nothing, and the run is labelled unverified rather than passed.

Trap 03

It can edit the question

The task description and the verifier are both just files in the repository, and the agent has write access to the repository. Rewriting the requirement is a much cheaper way to satisfy it than doing the work, and nothing about the resulting diff looks suspicious.

Fix: hash the contract files before the run and check the hashes afterwards. Changed contract means the round is forfeit, no matter how good the code looks.

Trap 04

The one who fixed it says it is fixed

The obvious loop is: review, repair, ask the repairer to confirm. It is also worthless. An agent asked to check work it just performed will approve it, in detail, with reasons.

Fix: the repair step and the re-review step must be separate invocations with no shared memory. The reviewer of a patch should not know it is looking at a patch, let alone its own.

Trap 05

It never ran the code, and nothing noticed

This one was invisible for a month. Claude ran under a permission mode that allowed file edits but required approval for shell commands. Nobody is present to approve anything in an unattended run, so every attempt to execute the tests was silently denied. The agent wrote the implementation entirely by reasoning, without running it once.

Codex accepted the code. The verifier passed. The pipeline exited zero. The only trace was one honest paragraph in the notes file the agent was asked to write: all of the above is manual reasoning; I was unable to execute anything. Not one automated stage caught it.

Fix: pre-authorise exactly one command, the verifier, and nothing else. That is enough for the agent to check itself, and too little for it to build the fake test from Trap 02.

Trap 06

The host quietly overrides your settings

I added knobs for which model to use and how hard it should think, with the convention that an empty value inherits the user's defaults. The variable names I chose collided with variables Claude Code injects into every subprocess it spawns. So the "inherit the default" path silently read the host's value instead and dialled the reasoning effort down — with no error, no warning, and a syntax check that passes cleanly.

Fix: namespace every configuration variable your script owns. Then verify by running the pipeline against stub binaries that print the arguments they actually received. Reading your own code proves nothing here.

Trap 07

"Stateless" is a claim, not a fact

Codex offers an ephemeral mode, documented as not persisting the session. I took that to mean I could run several at once. Watching file modification times showed it still writes to its local state database on every call. My original check had compared file counts, which never changed, so I had confidently concluded the opposite.

Fix: serialise anyway, with a real lock. And when you verify a claim, make sure the thing you measured is the thing you cared about.

The eighth, which is about me

After one run I re-tested the output myself rather than trusting the reviewer's summary, and found what looked like a genuine defect the whole pipeline had waved through. I was about to write it up as the headline finding.

The defect was in my test. My verification script hit a limit in the language runtime and reported it as the tested code's failure. The code was correct; the instrument was broken.

Checking by a second, independent route is the right instinct, and it is the one I lean on hardest. It is also not free: the second route is a piece of software too, written in a hurry, by someone who already believes he knows the answer. Independence buys you decorrelated errors, not zero errors.

What the pipeline actually bought

Three unattended runs of the same task. The task had five acceptance criteria, deliberately written so that the automated tests only covered three of them; the other two could only be caught by reading the code.

Run 1 Run 2 Run 3
Verdict Accept, first round Fix → repair → fresh reviewer accepted Fix → repair → fresh reviewer accepted
Did the writer run the code? No. Reasoned it out blind Yes Yes
Issues found by review None Two, both real One, real
Five acceptance criteria — Met after repair All met first try
My independent re-test 10 / 10 16 / 16 18 / 18

Between run 2 and run 3 I changed exactly one thing: I raised Codex's reasoning effort by one level. The difference was real — run 2 still left a defect for the reviewer to repair, while run 3 satisfied all five criteria on the first attempt and the only complaint was a stray cache file.

Run 1 looks like the better outcome and taught me nothing. Everything of value happened on the path where the reviewer said no: the objection, the repair, the second opinion from an agent with no stake in the repair, and only then the mechanical gate. A pipeline that has never rejected anything has not been tested; it has just been lucky.

The reviewer also earned its keep in a way I did not expect. One of the two objections was that the implementation had committed a cache file nobody asked for. That file only exists if the code was actually executed. The complaint was, incidentally, proof that Trap 05 had been fixed.

Where this does not apply

All of it rests on one thing: a verifier that returns pass or fail without an opinion. Where I have that, the machinery is worth its cost. Where I do not — the quality of a translation, whether a design is any good — there is nothing for the final gate to check, and a confident review from a second model is just a second opinion that also cannot be verified. The honest answer there is still a person reading the work.

The script is not published. It is welded to one operating system, one shell, and the exact install paths on my machine, and a clean clone would fail on someone else's laptop for reasons that have nothing to do with the ideas. The list above is the part that transfers.

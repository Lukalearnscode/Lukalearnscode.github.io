memoQ Tag Transfer

A command-line tool that restores inline formatting tags to translated text — and, more to the point, proves they landed on the right words. Open source, MIT licensed.

github.com/Lukalearnscode/memoq-tag-transfer

The problem

Game and software text is full of inline markup: a colour around a damage number, a link around a place name, a style span around one word in a sentence. Translation tools strip that markup out so the translator sees clean text, and it has to be put back afterwards.

Putting it back is deceptively hard. Word order changes between languages, so a tag that wrapped the third word in English might need to wrap the seventh in Chinese. Do it by hand across a few thousand segments and you will misplace some. You will not know which ones.

Source:  消耗 {green}40{/green} 点能量     ← the tag marks "40" as green
Target:  Consumes 40 Energy                ← markup gone after translation
Result:  Consumes {green}40{/green} Energy  ← restored automatically

Spot the error

Think that was easy? Here are five short segments. Each one looks fine. Each one is wrong. Try to find the problem before you read the answer. The sixth is a trick: it is not wrong, and the tool knows.

Source:  造成<color=#ff0000>150</color>点伤害
Target:  Deals 150 <color=#ff0000>Damage</color>

The red was on the number. Now it is on the word "Damage". Same tags, same count, same order, so every counting check passes. The side-by-side table catches it: the source span holds "150", the target span holds no number at all.

Source:  队伍会跟随<color=#ffe2af>当前队长</color>的移动
Target:  The party follows the current <color=#ffe2af>leader</color>

"Current" fell outside the highlight. Four Chinese characters went in, one English word came out. The table flags the span as probably shrunk.

Source:  使<style="q5">燃烧</style>的时间延长
Target:  extends <style="q5"></style>Burning duration

Both tags are there, in the right order, legally nested. Nothing is between them. "Burning" sits just after the closing tag. The table flags an empty span.

Source:  获得[gold]护盾[/gold]
Target:  Gain Shield

[gold] is not on any standard list of tags, so a checker that only knows the standard list never sees it. This one notices that [gold] and [/gold] both appear somewhere in the batch, decides the name is a tag, and reports two tags missing.

Source:  [gold]金币[/gold]和[blue]宝石[/blue]
Target:  [gold]Gold[/blue] and [blue]Gems[/gold]

The same four tags on both sides, so a count passes. But they are crossed: gold is closed by blue. A game engine draws that wrong, or crashes on it.

Source:  Pick {Amount:plural:an item|{} items} to sell.
Target:  选择{Amount}件物品出售。

The trick one. The English variable picks "an item" or "N items" at runtime. Chinese has no plural, so the translator folded it down to {Amount}. A strict checker calls that a lost tag. This tool gives a warning to glance at, not an error. On one game's official translation, that single difference was over eight hundred false alarms.

All six are in the repository as a runnable example. One command produces the report.

How it works

Unzip the memoQ file and read its XML. Classify every inline tag by type. Replace tags with numbered placeholders, hand the source and the plain translation to a language model, and let it insert the placeholders where they belong. Then verify, then write a TMX file for import back into memoQ.

Writing directly back into the original file format was the obvious approach and it was a dead end — ZIP structure, XML serialisation, namespace pollution, and CDATA handling each break memoQ compatibility in ways that produce a file which opens fine and is quietly wrong. TMX plus a local translation memory plus pre-translate is the path that survives contact with the actual software.

The part that turned out to be hard

Placement was not the hard problem. Verification was.

The easy checks are counting and comparison: the target must have the same number of tags as the source, the same tag content, legal nesting, consistent order for structural tags. All of that is mechanical and the tool does it segment by segment.

The check that matters is the one those cannot express. Every count can match, every tag can be present, nesting can be legal, order can be identical — and the tags can still be wrapped around the wrong words. The source colours a number; the target colours a verb. Nothing mechanical fires. The file passes and ships broken.

So the tool also emits a side-by-side table of what each tag pair actually wraps in source versus target, flags mismatched numbers automatically, and leaves the rest for a human to scan. It does not pretend to judge meaning. It makes the judgement cheap to perform.

What I got wrong along the way

The number-mismatch warning was originally written as a regular expression matching digits and periods. English periods and ellipses are made of periods. On a real file with 525 tags it produced 116 false warnings, all of them from sentences like "Wait... what?" — and a detector that cries wolf 116 times is worse than no detector, because after the twentieth false alarm nobody reads the twenty-first.

Each regression test in the repository exists because a bug like that one reached a real file first. They were not written for coverage.

Three more lessons, one summer later

The tool kept running on real files through the summer, and each of these bit me in turn.

A whitelist protects you from false alarms, and it also blinds you. The tool knows about forty-odd standard tag names such as [color] and [b]. It checks those and ignores everything else, which is what keeps [TODO] and [1] from setting off the alarm. But games invent their own tags. One file used [gold], [jitter] and half a dozen others, none of them on the list, so none of them were checked. When I measured, the tool was catching only fifteen to twenty per cent of the custom tags that went missing, while its report still said "count, content, order and nesting verified". The fix is small: any name that appears as both [x] and [/x] anywhere in the batch is a tag. [TODO] has no [/TODO], so it stays out.

A variable with a sentence inside it. Some engines write {Gems:plural:Gem|Gems}, and the game picks "Gem" or "Gems" at runtime. The part after the colon is text, and the translator is supposed to translate it. The tool treated the whole thing as one fixed token, so every translated option became a "tag content changed" error. On one game's official translation that was over eight hundred errors per direction, and when I sampled them, not one was real. Now only the name and the type count as the tag's identity. And when a Chinese translation drops the whole thing, because Chinese has no plurals, that is a warning to glance at, not an error that blocks delivery.

Two kinds of "the order changed". memoQ's own tags are anchored to a position in the sentence; if they swap places, something moved that should not have. But a tag like [gold]Gold[/gold] wraps a word, and when Chinese puts that word somewhere else in the sentence, the tag goes with it. That is a correct translation. The tool used to call both cases the same error. Now the second is a warning, and whether the tag still wraps the right word is left to the side-by-side table.

That table grew too. It started with one automatic flag, mismatched numbers. It now has five: mismatched numbers, a target pair that wraps nothing, a glossary term missing from the target span, a glossary term that crept into the target span from outside, and a span that is much longer or shorter than the source suggests. The last three need a glossary. No flag still does not mean pass. It means the machine has nothing to say, and a person should read that row.

Stack

Python, lxml for XML parsing, any OpenAI-compatible model for placement. No framework. Runs from one command. Verification needs no API key and no memoQ: hand it a JSON list of source and target pairs and it checks those.
